# Benchmarks

Generated by `npm run bench` (`bench/run.ts`). Every number below was measured on the
run that produced this file; nothing here is typed in by hand, which is the only way a
results file stays true after the code changes under it.

## What was measured on

| | |
| --- | --- |
| CPU | Apple M4 Pro |
| cores | 14 |
| memory | 48 GB |
| platform | darwin arm64 |
| Node | v18.20.2 |
| file store on | SSD, apfs |
| run took | 66 s |

The storage line matters more than any other: the file store fsyncs before resolving an
append, so every durable number in this report is a measurement of that device. On a
spinning disk they would be an order of magnitude worse, and on a device that lies about
fsync they would be an order of magnitude better and would mean nothing.

## How to read this

Every figure is a median over several runs with the observed range and standard deviation
beside it, written `median (min–max, sd)`. Where a range overlaps another row's range,
the two configurations are not distinguishable by this benchmark and the text says so
rather than picking the more flattering one. Timed regions are warmed up first — the
first run of anything in V8 measures the optimizing compiler — and the warm-up runs are
discarded.

Unflattering results are reported as found. There are three in here worth naming up
front: the fold is linear in history length with no snapshotting to bound it, the
optimistic-concurrency conflict rate reaches (N-1)/N — 94% at sixteen schedulers — and a
durable append costs 13.6 ms against microseconds in memory, which
is to say that durability, not event sourcing, is what the write path actually pays for.

One caution about comparing *this* file against another run of the same benchmark: the
fsync-bound numbers move by ten to twenty percent between whole-suite invocations on this
machine, which is more than several of the effects being measured. The spread beside each
figure is within one invocation, so rows are comparable with each other and less so with a
different run.

## 1. Projection cost vs history length

Folding one workflow's whole history with `project()`. The histories are generated
by `bench/fixtures.ts`: per step a `scheduled`, `leased`, `started`, a run of
`lease_extended` renewals, a `tool.requested`/`tool.succeeded` pair, and a
`completed`, ending in `workflow.completed`. Length is grown by adding renewals,
which is how a real history gets long: for a fixed graph, heartbeats are the only
event whose count is unbounded.

### Cost against history length (graph fixed at 8 nodes)

| events | fold (ms)                     | folds/sec | ns/event |
| ------ | ----------------------------- | --------- | -------- |
| 10     | 0.005 (0.005–0.009, sd 0.001) | 188,306   | 531      |
| 100    | 0.034 (0.034–0.035, sd 0.000) | 29,223    | 342      |
| 1000   | 0.366 (0.360–0.373, sd 0.004) | 2,734     | 366      |
| 10000  | 3.74 (3.72–3.94, sd 0.075)    | 267.5     | 374      |

**It is linear.** Per-event cost moves from 342 ns at
100 events to 374 ns at 10000 — a factor
of 1.09 across a 100x change in length — so the
total is proportional to the length of the log and the slope is flat enough that
nothing super-linear is hiding in it. The 10-event row sits higher per
event (531 ns) because at that length the fold is mostly
its own fixed setup: one mutable record per node, and the two maps.

What that implies at scale: the scheduler folds the full history of every active
workflow on every tick, so a workflow is not a fixed cost — it is a cost that rises
for as long as it lives. A step that heartbeats every five seconds for a day adds
~17k events, and at the rate above that single workflow spends on the order of a
millisecond of CPU per tick (measured: 6.36 ms for
17k events) purely to re-derive state it already derived on the previous tick. A few
hundred such workflows and the tick loop is the bottleneck.

**The fix is snapshotting, and it is not implemented.** The shape it would take is a
periodic materialized projection plus the sequence it was taken at, with the fold
resuming from there — `project()` is already a pure function of a prefix, and
`replayTo` already demonstrates that a prefix of the log is a valid log, so the
mechanism is available. Nothing in this repository does it. The honest statement is
that recovery and steady-state cost are both O(history) today, and the numbers below
are what that costs.

### Cost against graph size (history fixed at ~2,000 events)

| nodes | events | fold (ms)                     | ns/event |
| ----- | ------ | ----------------------------- | -------- |
| 4     | 2000   | 0.654 (0.641–0.672, sd 0.009) | 327      |
| 16    | 2000   | 0.869 (0.862–0.882, sd 0.006) | 434      |
| 64    | 2000   | 1.92 (1.86–1.94, sd 0.027)    | 960      |
| 256   | 2000   | 6.33 (6.22–6.43, sd 0.074)    | 3165     |

Per-event cost rises with the node count because `project()` recomputes readiness
after every event by looping over every node. That is a deliberate trade — it is what
makes it impossible for the scheduler to forget to mark a fan-in step ready — but it
means the fold is O(events x nodes), not O(events). For the graph sizes a workflow
definition realistically has (tens of nodes) the constant is small; for a generated
graph with hundreds, it dominates.

### `timeline()`, the debugging view

| events | timeline (ms)              |
| ------ | -------------------------- |
| 100    | 1.89 (1.81–3.79, sd 0.762) |
| 400    | 31.3 (30.7–32.4, sd 0.574) |
| 1600   | 490 (489–496, sd 2.56)     |

Quadratic, as its own comment says it is: it folds every prefix so that the
transitions it prints come from the same state machine the scheduler uses rather than
from a second implementation that could disagree. The numbers say that choice is free
for the few hundred events a human reads and unusable past a few thousand, which
matches where it is used — the CLI and the dashboard, on one workflow at a time.

## 2. Append throughput: memory store vs file store

Single-event appends to one workflow, driven straight at the store with no scheduler
in the way. Both stores run the same `sealBatch` validation and the same observer
notification, so the difference is the durable write.

### Headline

| store        | appends/run | runs | per append (ms) | appends/sec | run total (ms)             |
| ------------ | ----------- | ---- | --------------- | ----------- | -------------------------- |
| memory       | 5,000       | 5    | 0.002           | 485,351     | 10.3 (9.22–11.4, sd 0.678) |
| file (fsync) | 60          | 3    | 13.6            | 73.6        | 815 (798–828, sd 12.3)     |

Durability costs a factor of **6592x** on this machine and
filesystem: 0.002 ms per append in memory against 13.6 ms
on disk. That is the number to quote when someone asks what event sourcing costs — it
is not the fold, it is the fsync. Note what the file store buys for it: an
acknowledged event is recoverable after power loss, every line carries a checksum, and
a torn final line is repaired on read rather than being read as a plausible event.

The memory store is not a toy that skips the work — it round-trips every event through
`JSON.parse(JSON.stringify(...))` on append specifically so a payload the file store
would mangle misbehaves identically. Some of its per-append cost is that round trip.

### Batching amortizes the fsync (file store)

| events/append | per append (ms) | appends/sec | events/sec |
| ------------- | --------------- | ----------- | ---------- |
| 1             | 13.8            | 72.2        | 72.2       |
| 4             | 14.1            | 71.2        | 284.7      |
| 16            | 14.3            | 70.0        | 1,120      |
| 64            | 14.7            | 67.9        | 4,346      |

One fsync per append regardless of how many events it carries, so events per second
rises almost linearly with batch size while appends per second barely moves. The
practical consequence: the atomic multi-event appends the scheduler already writes for
a retry decision or a workflow completion are free compared to writing them one at a
time, and a caller with a backlog should batch.

### Per-append cost against the number of workflows already in the store

| workflows in store | per append (ms) | appends/sec |
| ------------------ | --------------- | ----------- |
| 1                  | 13.8            | 72.3        |
| 64                 | 13.9            | 72.1        |
| 256                | 14.6            | 68.3        |
| 1,024              | 14.7            | 67.9        |

The index rewrite does **not** dominate at these sizes: per-append cost moves by
a factor of 1.07 between
an almost-empty store and one holding 1,024 workflows. The mechanism is still
O(workflows) per append by construction — `writeIndex()` reserializes every entry
and fsyncs the result after every durable write — but on this device two fsyncs
and a directory sync cost far more than serializing a thousand small objects, so
the quadratic term is buried under a constant until the workflow count is much
larger than anything measured here.

Reported because it would have been easy to leave out: the number is unexciting,
and the mechanism is the kind that is usually described as a problem without
anyone checking whether it currently is one. At these sizes it is not.

One caveat on reading this table across to a real deployment: these appends are
sequential, so each one gets an index write of its own. Concurrent appends to
*different* workflows share one — `writeIndex` keeps a single write in flight with
at most one queued behind it — so a busy control plane pays less per append here
than this table suggests, not more.

### Payload size

| output bytes | memory (ms) | memory appends/sec | file (ms) | file appends/sec |
| ------------ | ----------- | ------------------ | --------- | ---------------- |
| 64           | 0.003       | 307,051            | 12.2      | 82.0             |
| 4,096        | 0.013       | 78,594             | 13.2      | 75.6             |
| 65,536       | 0.142       | 7,043              | 14.5      | 69.2             |

The file store does not move at all across a 1,000x range of payload size: the fsync
dominates so completely that writing 64 KiB costs what writing 64 bytes costs. The
memory store, having no fsync to hide behind, is a straight serialization cost and
scales with the payload — which is also the best available estimate of how much of the
file store's 14 ms is *not* the device.

## 3. Optimistic-concurrency contention

24 independent ready steps in one workflow, N schedulers racing to lease them.
Each scheduler loops: read the history, fold it, ask `readySteps` what may run, call
`LeaseManager.acquire` on the first candidate, and — win or lose — go round again
against the fresh history. It stops when the fold offers nothing. No locks anywhere;
the only arbitration is the store's `expectedSequence` check.

**Every run asserts that each step was leased exactly once.** A run that violated it
would throw rather than print, so the numbers below are only produced when the
mechanism held.

### Memory store

| schedulers | wall (ms)                  | leases/sec | acquire calls | conflicts | conflict rate |
| ---------- | -------------------------- | ---------- | ------------- | --------- | ------------- |
| 1          | 4.63 (3.65–7.18, sd 1.26)  | 5,186      | 24.0          | 0.0       | 0%            |
| 2          | 1.52 (1.39–7.24, sd 2.45)  | 15,799     | 48.0          | 24.0      | 50%           |
| 4          | 2.78 (2.59–3.41, sd 0.295) | 8,646      | 96.0          | 72.0      | 75%           |
| 8          | 5.11 (4.49–5.56, sd 0.408) | 4,699      | 192.0         | 168.0     | 88%           |
| 16         | 8.16 (7.64–8.34, sd 0.278) | 2,940      | 384.0         | 360.0     | 94%           |

### File store (fsync per append)

| schedulers | wall (ms)              | leases/sec | acquire calls | conflicts | conflict rate |
| ---------- | ---------------------- | ---------- | ------------- | --------- | ------------- |
| 1          | 357 (319–375, sd 23.1) | 67.3       | 24.0          | 0.0       | 0%            |
| 2          | 384 (374–389, sd 6.26) | 62.5       | 48.0          | 24.0      | 50%           |
| 4          | 398 (364–416, sd 21.4) | 60.4       | 96.0          | 72.0      | 75%           |
| 8          | 428 (424–442, sd 8.02) | 56.0       | 192.0         | 168.0     | 88%           |

### Reading it

At N=1 the conflict rate is zero and the acquire count equals the step count: with one
scheduler there is nothing to race. As N rises, every lease costs exactly N attempts —
one winner and N-1 losers, each of which has already paid for a read and a fold before
discovering it lost. The conflict rate is therefore (N-1)/N: 50% at two schedulers, 94%
at sixteen. Correct throughout, and wasteful in a way that grows with the fleet.

**The conflict rate is identical in both stores**, to the event. That is worth
stating because the opposite would have been the natural guess: the file store's
window between folding a history and appending against it is milliseconds rather
than microseconds, so one would expect more losers to fit inside it. They do not,
because the losers are synchronized by the same thing that creates them — every
scheduler reads the same head, exactly one append wins, and the rest discover it
together and retry together. The window width changes how long a round takes; it
does not change how many schedulers are in it. A wider window would only raise the
conflict rate if arrivals were independent of each other, which here they are not.

A caveat on the wall-clock column: N=1 and N=2 overlap in range; N=2 and N=4 overlap in range. Those
configurations are not distinguishable by this benchmark, and reading an ordering into
them would be reading noise. The conflict counts, which are integers and identical
across runs, are the part of this table to trust.

Wall-clock throughput degrades gently rather than collapsing: 4.63 ms at
one scheduler against 8.16 ms at 16 on the memory
store, for the same 24 leases. The wasted work is reads and folds, which are cheap; what
the fleet pays is CPU, not latency. On the file store the wall time barely moves with N
at all (357–428 ms across the range) because the number of *successful* appends is
the same 24 either way, and fsyncs dominate everything else.

So: correct at every N measured, efficient only at small N. This is a design for a
handful of schedulers, not for fifty. Past that point the honest fix is not a lock — it
is partitioning, so two schedulers rarely contend for the same workflow in the first
place. Nothing in the current design prevents that, and the optimistic check stays as
the safety net for the overlap at a partition boundary, which is the role it is good at.

What this benchmark does **not** measure: schedulers in separate processes. Everything
here shares one event loop, so a "concurrent" scheduler is one that interleaves at an
`await`. That is the right model for the arbitration being tested — the store is the
only shared state and its check is the only arbiter — but a real deployment adds network
latency inside the conflict window and a store that can be written by a peer this
process cannot see.

## 4. Recovery time vs log size

Each row seeds a file store with a given number of workflows, each carrying a history
of a given length, then drops the store object and does what a restarted control plane
does: `FileEventStore.open` on the same directory, `listActive()`, and a read plus a
fold per active workflow. Nothing is carried in memory across the boundary.

Half the seeded workflows are left incomplete — no terminal event — so `listActive`
has something to exclude and the "active" column is not just the workflow count. That
matters: recovery cost is driven by the *active* set, and a store full of finished
workflows is cheap to recover from no matter how large it is.

### Recovery, index intact

| workflows | events each | events total | active | open (ms) | read+fold (ms) | total (ms) | ns/replayed event |
| --------- | ----------- | ------------ | ------ | --------- | -------------- | ---------- | ----------------- |
| 10        | 100         | 1,000        | 5      | 1.67      | 4.19           | 5.86       | 11957             |
| 100       | 100         | 10,000       | 50     | 6.18      | 19.9           | 26.1       | 5325              |
| 100       | 1,000       | 100,000      | 50     | 7.11      | 101            | 108        | 2158              |
| 500       | 200         | 100,000      | 250    | 16.3      | 132            | 148        | 2994              |

`open` is cheap and nearly flat in the event count, because with a valid index it only
`stat`s each log file and compares the size — a workflow whose file is the length the
index says is not read at all. It scales with the *number* of workflows, not with their
length. The read-and-fold phase is where recovery time actually goes, and it is linear
in the number of events in the active set, at a per-event cost in the same range
benchmark 1 measured for the fold alone plus the cost of reading and checksumming each
line. The last column divides total recovery time by the events actually replayed —
the active half — rather than by everything on disk.

The claim holds: recovery is a replay, it is linear, and there is no step in it that
can be done wrong — but it is also not free, and it is the same O(history) cost as the
steady-state fold. A control plane holding a large active set restarts in time
proportional to the total length of every unfinished workflow it owns. Snapshotting
would fix this and recovery at the same time; it is still not implemented.

### Recovery with the index deleted

| workflows | events total | open with index (ms) | rebuild (ms) | penalty |
| --------- | ------------ | -------------------- | ------------ | ------- |
| 10        | 1,000        | 1.67                 | 12.8         | 8x      |
| 100       | 10,000       | 6.18                 | 42.6         | 7x      |
| 100       | 100,000      | 7.11                 | 180          | 25x     |
| 500       | 100,000      | 16.3                 | 261          | 16x     |

With no index, `open` reads and verifies every log in full before answering a single
question. The penalty is large and the behaviour is correct: the index is a cache,
the logs are the truth, and the store recovers from losing the cache without losing an
event. The number is the cost of that guarantee being real rather than aspirational.

## 5. End-to-end workflow latency

A real `Scheduler` on the system clock, memory store, diamond DAG:
`fetch -> {classify, score} -> join -> finalize`. The dispatcher sleeps
5 ms per step to stand in for a tool call, so 5 steps of simulated work
is 25 ms with a critical path of 20 ms (the two analyses
overlap). Timed from `submit` returning to the `workflow.completed` event arriving on
the store's own `subscribe`.

Store time is measured by a decorator around the `EventStore` handed to the scheduler —
legal precisely because the scheduler depends on the interface and not on a class.

### Latency against tick interval

| tick (ms) | wall median | min  | max  | tool (path) | tool (sum) | appends | reads | unaccounted | # appends | # reads |
| --------- | ----------- | ---- | ---- | ----------- | ---------- | ------- | ----- | ----------- | --------- | ------- |
| 50        | 77.5        | 76.2 | 78.4 | 24.8        | 31.1       | 0.248   | 0.086 | 52.3        | 16        | 28      |
| 5         | 32.1        | 31.1 | 33.3 | 24.7        | 30.8       | 0.363   | 0.084 | 6.97        | 16        | 34      |
| 1         | 23.1        | 20.3 | 23.6 | 20.9        | 26.1       | 0.229   | 0.114 | 1.83        | 16        | 59      |

All times in milliseconds, over 7 runs. **tool (path)** is the tool time on the
critical path — `fetch`, then the slower of the two analyses, then `join`, then
`finalize` — and **tool (sum)** is the total across all five steps. The two differ
because the analyses run concurrently, and only the first is comparable with wall
time. Subtracting the sum instead, which is the easy mistake, produces a negative
"unaccounted" column and an unreadable table: that was the first version of this
benchmark, and it was wrong.

### Where the time goes

At a 50 ms tick the workflow takes 77.5 ms to do
24.8 ms of critical-path work. At a 1 ms tick the same workflow takes
23.1 ms. The difference is not computation — the append and read
totals barely move between the two rows — it is time spent waiting for the loop to come
round. The scheduler re-ticks immediately when a step completes, so the chain after the
first dispatch is event-driven; what the tick interval buys is the delay before the
*first* dispatch and the delay after any retry backoff.

Store work is real but small on the memory store: 0.229 ms of appends
across 16 appends and 0.114 ms of reads across 59
reads. Note the read count: every scheduler decision reads the whole history, and a
five-step workflow does it dozens of times. On the file store, at the
13.6 ms per append benchmark 2 measured on this machine, those
16 appends alone would cost about
217 ms — which is the honest answer to "what
does this cost in production": the tick interval stops being the dominant term and the
fsyncs take over. That is an extrapolation, not a measurement; the two numbers it
multiplies are both measured in this run.

With the tool sleep removed entirely the same workflow completes in
6.33 ms (5 ms tick), which is the floor this control plane
imposes on a workflow that does no work at all.

### What this benchmark cannot tell you

It runs one workflow at a time on one scheduler with an in-memory store, so it measures
latency and not capacity. It says nothing about what happens when a hundred workflows
tick at once, which is where the projection cost from benchmark 1 and the contention
cost from benchmark 3 would start to interact — and that interaction is the thing most
likely to be the real limit. Measuring it needs a load generator this does not have.
